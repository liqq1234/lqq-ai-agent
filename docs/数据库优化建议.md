# 数据库优化建议

## 📊 现状分析

### 当前表结构
1. **users** - 用户表 ✅
2. **app** - 应用表 ✅
3. **ai_chat_memory** - 消息记录表 ⚠️

### 存在问题

#### 1. 缺少对话表
- **问题**：只有消息表，没有对话（conversation）的元信息管理
- **影响**：无法管理对话标题、对话列表、对话排序等
- **chat_id** 只是字符串标识，没有对应的实体表

#### 2. 命名规范不统一
- `ai_chat_memory` 使用下划线命名：`create_time`, `user_id`
- `app` 使用驼峰命名：`appName`, `createTime`, `userId`
- `users` 混用：`user_name`（下划线） + `created_at`（下划线）

#### 3. 删除标记字段不统一
- `ai_chat_memory.is_del`
- `app.isDelete`
- `users.deleted`

#### 4. chat_id 数据类型问题
- 当前：`VARCHAR(32)` - 字符串类型
- 问题：性能较差，无法建立外键约束
- 建议：改为 `BIGINT`，关联到 conversation 表

## 💡 优化方案

### 方案 A：渐进式升级（推荐）⭐

#### 优点
- 兼容现有数据
- 风险小，可回滚
- 保留 chat_id 作为过渡

#### 步骤
1. ✅ 创建 `conversation` 表
2. ✅ 在 `ai_chat_memory` 中添加 `conversation_id` 字段
3. ✅ 迁移现有数据：为每个唯一的 `chat_id` 创建 conversation 记录
4. ✅ 更新 `ai_chat_memory` 的 `conversation_id`
5. ✅ 添加外键约束
6. ⏸️ 保留 `chat_id` 一段时间（1-2周）作为备份
7. 🗑️ 确认无问题后删除 `chat_id` 字段

#### 执行脚本
```sql
-- 见 upgrade_conversation.sql
```

---

### 方案 B：一步到位重构

#### 优点
- 表结构更清晰
- 命名规范统一
- 性能更优

#### 步骤
1. 创建新表结构（conversation + message）
2. 数据迁移
3. 重命名表：`ai_chat_memory` → `message`
4. 统一所有表的命名规范

#### 风险
- 需要同步修改所有代码
- 一次性改动较大
- 需要停机维护

## 📋 优化后的表结构

### conversation 表
```sql
id          BIGINT          主键
user_id     BIGINT          用户ID（外键 → users.id）
title       VARCHAR(255)    对话标题
create_time DATETIME        创建时间
update_time DATETIME        更新时间
is_deleted  TINYINT(1)      删除标记
```

### ai_chat_memory 表（优化后）
```sql
id              BIGINT      主键
conversation_id BIGINT      对话ID（外键 → conversation.id）
user_id         BIGINT      用户ID（外键 → users.id）
role            VARCHAR(20) 消息角色（user/assistant）
content         TEXT        消息内容
create_time     DATETIME    创建时间
update_time     DATETIME    更新时间
is_deleted      TINYINT(1)  删除标记
```

## ⚠️ 注意事项

### 1. 数据备份
```bash
# 备份整个数据库
mysqldump -u root -p your_database > backup_$(date +%Y%m%d_%H%M%S).sql

# 只备份 ai_chat_memory 表
mysqldump -u root -p your_database ai_chat_memory > ai_chat_memory_backup.sql
```

### 2. 事务处理
- 所有迁移操作应在事务中执行
- 遇到错误及时回滚

### 3. 外键约束
- 确保 `users` 表中的用户数据存在
- 迁移前检查数据一致性

### 4. 索引优化
- 对话列表查询：`idx_user_id`, `idx_create_time`
- 消息查询：`idx_conversation_id`, `idx_conversation_user`

## 📊 性能对比

### 优化前
```sql
-- 查询用户的所有对话（需要扫描全表+去重）
SELECT DISTINCT chat_id, user_id 
FROM ai_chat_memory 
WHERE user_id = 100 
  AND is_del = 0;
```

### 优化后
```sql
-- 直接从对话表查询（索引查询）
SELECT id, title, create_time, update_time
FROM conversation
WHERE user_id = 100 
  AND is_deleted = 0
ORDER BY update_time DESC;
```

**性能提升**: 约 10-100 倍（取决于数据量）
